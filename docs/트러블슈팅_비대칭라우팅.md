# 트러블슈팅 — 비대칭 라우팅 (재택 VPN → DMZ 웹 타임아웃)

## 1. 기록된 사실 (발표자료 슬라이드 11~12)
- 재택 PC(VPN 100.2) → `http://192.168.102.10` 타임아웃
- pfSense OpenVPN 룰은 Pass, States 에 세션·트래픽이 보임 → **요청은 Rocky 까지 도착**
- Rocky 의 응답이 VPN 대역(100.0/24)으로 돌아오지 못해 유실
- Outbound NAT(Hybrid)로 VPN 대역을 DMZ 주소(102.1)로 마스커레이드하자 **즉시 해결**

## 2. NAT 로 풀렸다는 것이 말해 주는 것
```
NAT 전: Rocky 가 받은 요청의 출발지 = 192.168.100.2 (다른 망)
        → 응답은 Rocky 라우팅 테이블에서 "100.2 로 가는 길" = 보통 기본 게이트웨이로 나감
NAT 후: Rocky 가 받은 요청의 출발지 = 192.168.102.1 (같은 망, 온링크)
        → 응답은 라우팅 없이 같은 망으로 바로 감 → 성공
```
즉 **Rocky 에서 100.0/24 로 가는 경로가 pfSense(102.1)가 아니었다**고 보는 게 가장 자연스럽다.
발표자료에는 "Rocky 기본 GW = 102.1"로 적혀 있지만, 당시 실제 Rocky 의 라우팅 테이블은 증빙이 없다(2일차 "라우팅 증빙"이 예정 상태).

## 3. 함께 겪은 문제 — 호스트 PC 의 Windows 프록시 (2026-11-10 기억, 정정 반영)
- **관찰**: VM 들을 돌리던 **호스트 PC(Windows)** 에 Windows 설정의 프록시가 켜져 있었고, ping 이 나가기만 하고 응답이 돌아오지 않았다. **프록시를 끄자 해결**됐다.
- **원리상 맞지 않는 점**: Windows 설정의 프록시(설정 → 네트워크 → 프록시 / 인터넷 옵션)는 브라우저 같은 HTTP·HTTPS 프로그램에만 적용된다. **ping(ICMP)은 프록시를 타지 않는다.** 그래서 "프록시 설정 때문에 ping 응답이 안 왔다"는 메커니즘은 확인되지 않는다.
- **그런데도 끄니 해결됐다면 가능한 설명** (확인 안 됨)
  1. 같은 시점에 다른 변경이 함께 있었다 — Windows ICMP 인바운드 허용(`netsh`, 발표자료 Phase 4), Outbound NAT 적용, 어댑터 재연결 등
  2. 그 프록시 설정을 넣은 **프로그램**이 따로 있었고, 그 프로그램이 가상 어댑터·경로를 바꾸고 있었다 (설정을 끄며 프로그램도 정리됐을 수 있음)
  3. 호스트의 VMware 가상망(VMnet) 쪽 상태가 재연결로 초기화됐다
- 2026-11-10 처음 정리할 때 "Rocky 인터넷 문제"로 적었던 것은 **잘못** — 실제로는 호스트 PC 의 Windows 프록시였다.

| 문제 | 장비 | 해결 | 원리 확인 |
|---|---|---|---|
| 재택 VPN → DMZ 웹 타임아웃 | Rocky 의 응답 경로 | Outbound NAT (Hybrid) | ✅ 비대칭 라우팅으로 설명됨 (발표자료 기록) |
| ping 이 나가고 응답 없음 | 호스트 PC (Windows 프록시 켜짐) | 프록시 끔 | ❓ 프록시는 ICMP 에 무관 — 동시 변경 여부 미확인 |

두 증상이 같은 사건이었는지(같은 원인)도 기록이 없어 알 수 없다.

### 다음에 같은 일이 생기면 (원인을 확정하는 법)
- **한 번에 하나만 바꾼다.** 프록시만 끄고 → 확인, 다시 켜고 → 재현되는지. 재현되면 진짜 원인.
- 호스트에서: `route print`(경로·가상 어댑터), `netsh winhttp show proxy`(시스템 WinHTTP 프록시), 설치된 프록시·VPN 프로그램 확인
- Wireshark 를 VMnet 어댑터에 걸고 echo request / reply 가 어디까지 가는지 확인

### 비대칭 라우팅의 진짜 원인 후보 (확인 안 됨)
| 후보 | 가능성 | 근거 |
|---|---|---|
| **A. 인터넷용으로 NIC 를 하나 더 붙임** (예: VMware NAT 어댑터) → 기본 경로가 그쪽 | **가장 유력** | 인터넷이 안 될 때 흔히 NAT 어댑터를 추가한다. 그러면 기본 경로가 그 NIC 로 잡혀 100.2 로 가는 응답이 pfSense 가 아니라 그쪽으로 나가 사라진다. Outbound NAT 로 출발지를 102.1(온링크)로 바꾸면 이 경로를 안 타서 해결된 것과 맞다 |
| B. 100.0/24 를 덮는 정적 경로 | 가능 | 다른 목적으로 넣은 경로가 VPN 대역과 겹친 경우 |
| C. 역경로 필터(rp_filter) | 가능 | NIC 가 여럿일 때 커널이 "다른 NIC 로 와야 할 패킷"을 버림. A 와 함께 나타나기 쉬움 |
| (참고) 호스트 Windows 프록시 | 원리상 직접 원인 아님 | 시스템 프록시는 HTTP·HTTPS 에만 적용. 다만 프록시를 넣은 프로그램이 경로를 바꿨다면 A·B 와 같은 효과 |

## 4. 다음에 같은 증상이면 (확인 명령)
```bash
# Rocky 에서
ip route                              # 기본 경로가 어느 NIC·게이트웨이인가
ip route get 192.168.100.2            # 응답이 실제로 어느 NIC 로 나가나 ← 한 줄로 판정
ip -br addr                           # NIC 가 몇 개인가
env | grep -i proxy; grep -i proxy /etc/dnf/dnf.conf   # 프록시 설정 (인터넷이 안 될 때 먼저 볼 것)
sysctl net.ipv4.conf.all.rp_filter    # 1 이면 엄격 모드
sudo tcpdump -ni any host 192.168.100.2   # 요청이 들어오는 NIC 와 응답이 나가는 NIC 비교
```
`ip route get 192.168.100.2` 결과가 `via 192.168.102.1 dev <DMZ NIC>` 가 아니면 비대칭이다.

## 5. 정석 해결 (출발지 IP 보존)
1. Rocky 기본 경로를 pfSense(102.1)로 — 인터넷도 pfSense 를 거치게 한다(DMZ → any 허용 룰 이미 있음)
2. 추가 NIC 가 꼭 필요하면 기본 경로는 102.1 에 두고, 그 NIC 에는 필요한 대역만 정적 경로
3. 또는 VPN 대역만 명시: `sudo ip route add 192.168.100.0/24 via 192.168.102.1` (영구 반영은 `nmcli connection modify <DMZ연결> +ipv4.routes "192.168.100.0/24 192.168.102.1"`)
4. 그 뒤 Outbound NAT 규칙을 끄고 Rocky `access_log` 에 100.2 가 찍히는지 확인

## 6. 관제 관점
- NAT 로 덮으면 Rocky·Apache 로그의 출발지가 전부 102.1 → **누가 접속·공격했는지 서버 로그로는 알 수 없음**
- 같은 문제를 2026-11 팀 프로젝트에서 다시 만남: 앱 로그 client_ip 가 127.0.0.1(WAF 프록시 뒤) → mod_remoteip 로 복원
- 면접 답변: "방화벽은 통과인데 응답이 없으면 응답 경로부터 봅니다. NAT 로 우회하면 서버 로그에서 실제 IP 가 사라지므로, 관제 목적이면 라우팅을 바로잡는 쪽을 택합니다."
